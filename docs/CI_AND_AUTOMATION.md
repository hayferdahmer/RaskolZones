# CI и автоматизация RaskolZones

## Текущий GitHub Actions workflow

Файл `.github/workflows/ci.yml` запускается при push в `main`, pull request в `main` и вручную.

На текущем этапе репозиторий ещё не содержит Maven- или Gradle-конфигурации, поэтому workflow:
- проверяет README, канонический журнал решений и производное техническое задание;
- проверяет обязательные архитектурные разделы A-00–A-40, все восемь подпунктов A-38, A-39 и A-40 и актуальность истории решений в ТЗ;
- проверяет обязательные ссылки README и отсутствие trailing whitespace в основных документах;
- автоматически запускает Maven `verify`, если появится `pom.xml`;
- иначе запускает Gradle `check`, если появится `gradlew`;
- явно сообщает, если сборка пока невозможна из-за отсутствия build descriptor.

Java 25 уже задана в CI как целевая версия проекта. Maven cache пока не включён: до появления `pom.xml` он мешает настройке Java. Кэширование можно вернуть после появления Maven build descriptor. До появления исходников и build descriptor успешный workflow означает только прохождение документационных проверок, а не готовность плагина к запуску.

## План проверок и workflow-ботов

Автоматизацию следует вводить по мере появления проверяемого объекта, разделяя обязательные CI gates и вспомогательные отчёты.

1. **Build & Test** — компиляция на Java 25, unit-тесты, интеграционные тесты Paper, проверка совместимости API.
2. **Formatting** — Spotless или эквивалент: форматирование Java, проверка форматирования без автоматической записи в PR.
3. **Static Analysis** — SpotBugs, Error Prone и/или PMD после оценки совместимости с Java 25; анализ должен быть воспроизводимым.
4. **Dependency & Supply Chain** — проверка уязвимостей зависимостей, фиксация версий Actions, SBOM и лицензий.
5. **Security Auditor** — отдельный отчёт по опасным API, permissions, обработке пользовательского ввода, SQL, файловым операциям и границам потоков. На первом этапе — advisory; блокирующие правила вводятся только после проверки ложных срабатываний.
6. **Documentation/API Compatibility** — проверка публичного API, SemVer, Javadocs и примеров интеграции.
7. **Release Verification** — сборка релизного артефакта, тесты, подпись/контрольные суммы и публикация только после прохождения обязательных gates.

## Политика ботов

- Боты не получают write-доступ к `main` и не меняют исходники автоматически.
- Автоматические исправления предлагаются отдельным pull request или как patch/artifact.
- Блокирующие проверки должны иметь ясные критерии, диагностические сообщения и воспроизводимый результат.
- Секреты не выводятся в логи; workflow использует минимальные permissions.
- Не добавлять одновременно несколько инструментов, проверяющих одно и то же: каждый бот должен иметь отдельную ответственность.
- Любая проверка, требующая Paper runtime, выполняется на тестовом сервере/фикстурах, а не имитируется обычной компиляцией.

## Текущие ограничения

Каноническим источником решений является `docs/ARCHITECTURE_DECISIONS.md`; `docs/TECHNICAL_SPECIFICATION.md` синхронизируется с ним при каждом утверждённом раунде. README остаётся краткой точкой входа. CI проверяет структуру и ключевые признаки согласованности, но не заменяет смысловое архитектурное ревью.

Пока в репозитории нет исходного кода, build descriptor, тестов и конфигурации плагина. Поэтому нельзя честно включить компиляцию, тесты Paper, анализ Java-кода или аудит зависимостей. Эти jobs добавляются после появления соответствующих файлов и согласования структуры сборки.
