# RaskolZones — дорожная карта разработки

> Актуальность: 12 ноября 2026 г.  
> Целевая платформа: Paper 26.2, Java 25.  
> Статус проекта: реализация инженерного фундамента; JAR собирается и проходит CI runtime smoke test, функциональный MVP/Alpha ещё не готов.  
> Дорожная карта описывает контрольные результаты, а не обещанные календарные сроки.

## Принцип выпуска

RaskolZones будет выпускаться поэтапно. Не требуется ждать завершения всех интеграций и второстепенных функций, чтобы впервые установить плагин на тестовый сервер. Первый устанавливаемый Alpha-релиз появится после готовности минимального вертикального среза, который реально запускается на целевой версии Paper, сохраняет данные и позволяет проверить базовую работу территорий.

Каждый этап проходит автоматические проверки, а функции, не прошедшие проверку, не включаются в релиз только ради формального выполнения плана.

## Этап 0. Архитектурное проектирование

**Статус: завершён переходом к реализации (A-43).**

- Завершить раунды архитектурных решений A-00 и далее.
- Зафиксировать модель геометрии, иерархии, пересечений и разрешения конфликтов.
- Определить игровые политики PvP/PvE, строительства и взаимодействий.
- Уточнить публичный API, контракты интеграций, жизненный цикл, миграции и модель безопасности.
- Подготовить итоговое техническое задание, границы MVP и критерии приёмки.

**Результат:** согласованная спецификация, по которой можно реализовывать систему без постоянного пересмотра фундаментальных решений.

## Этап 1. Инженерный фундамент

**Статус: foundation, первая итерация Territory Core / Spatial Query Engine и базовый Territory Transition Engine реализованы.**

- Создать Java 25 / Paper 26.2 проект, Maven-сборку и структуру модульного монолита.
- Реализовать bootstrap, конфигурацию, логирование, lifecycle и health-состояние.
- Настроить CI: компиляция, unit-тесты, форматирование, статический анализ и проверка зависимостей.
- Реализовать загрузку/выключение плагина, конфигурацию, локализацию, логирование и диагностику.
- Создать storage-интерфейс и SQLite-реализацию с версионированием схемы.
- Реализовать World Registry: UUID-идентичность миров, автоматическое обнаружение загрузки/выгрузки, сохранение записей и восстановление после повторной загрузки.
- Реализовать базовую модель территории и внутренние контракты Territory Core: UUID, типы, иерархия, cuboid/polygon, SQLite repository, optimistic version и архивирование.
- Реализовать первую итерацию Spatial Query Engine: immutable snapshots, grid index, overflow для крупных областей, точный point query, invalidation и lifecycle миров.
- Реализовать базовый Territory Transition Engine: состояние игрока, enter/exit, выборка траектории движения с шагом до блока, телепортации/порталы, смена миров и Paper event для интеграций.

**Критерий выхода:** проект стабильно собирается; тесты проходят; плагин загружается и корректно выключается на тестовом Paper 26.2; SQLite мигрирует и сохраняет реестр миров и территорий; Paper runtime smoke test подтверждает запуск и схему v3.

## Этап 2. Первый устанавливаемый MVP / Alpha

**Статус: не начат. Это первая контрольная точка для установки на сервер пользователя.**

Минимальный функциональный вертикальный срез:

- Плагин устанавливается как обычный Paper JAR без клиентских модов.
- Создаёт и проверяет конфигурацию и SQLite-хранилище.
- Запускается, сообщает о готовности и корректно выключается.
- Администратор может создать, посмотреть, изменить и удалить/архивировать базовую территорию через команды.
- Поддерживаются первые геометрические формы и границы по Y.
- Игрок при перемещении корректно определяется как находящийся внутри или вне территории.
- Работают базовые правила защиты территории и permissions.
- Изменения переживают перезапуск сервера.
- Есть диагностика, журнал ошибок и инструкция установки.
- Пройдены unit-тесты, интеграционные тесты и ручной smoke test на чистом Paper 26.2 + Java 25.

**Критерий выпуска Alpha:** опубликован JAR с номером версии, контрольной суммой, инструкцией установки, известными ограничениями и подтверждённым запуском на тестовом сервере.

На этом этапе пользователь уже сможет поставить плагин на отдельный тестовый сервер и проверять реальное поведение. Alpha не будет означать завершённость всего ТЗ.

## Этап 3. Географическое ядро и редактор

**Статус: в работе — реализованы Rule Resolution Engine, SQLite Rule Registry (schema v4), Type Rule Profiles (schema v5), наследование по иерархии и первая доменная итерация Contextual Rule Engine.**

- Составные территории, отверстия и расширенные геометрические операции.
- Расширение и нагрузочная оптимизация обработки перемещений и переходов игроков, кэширование результатов запросов и активных контекстов.
- Нагрузочная калибровка spatial grid и сравнение альтернативных индексов.
- Подключить предметные политики PvP/PvE/build/interactions к Evaluation Pipeline.
- Расширить типизированные условия контекстом субъекта, цели, события, мира и координат (первая доменная итерация уже реализована); далее — хранение условий в SQLite, привязка к прямым правилам/профилям и применение до resolver.
- Реализовать receipts A-39/A-40 и enforcement listeners с атомарной повторной проверкой актуальности.
- Полноценные редакторские сессии, черновики, Undo/Redo и визуализация.
- Массовые операции с предварительным просмотром и подтверждением.

**Критерий выхода:** корректность геометрии и конфликтов подтверждена тестами, включая сложные пересечения, телепортации и быстрые перемещения; матрица A-37/A-38, fail-closed resolver, Rule Registry, типовые профили и наследование покрыты тестами; прикладные политики, receipts и enforcement остаются в работе.

## Когда можно будет впервые установить плагин

Первая установка на сервер пользователя планируется на **Этапе 2 — MVP / Alpha**, сразу после выполнения всех критериев выпуска Alpha. Для этого не нужно ждать окончания этапов 3–7.

Инженерный JAR уже собирается и проверяется на тестовом Paper 26.2, однако это ещё не Alpha: управление территориями, геометрия, защита и права не реализованы. Сборка, которая только загружается и создаёт базу, не считается готовым игровым плагином.

Для первой игровой проверки рекомендуется отдельный тестовый сервер или копия мира, а не основной игровой сервер. Перед Alpha будут опубликованы точная версия, инструкция установки, перечень реализованных функций и известных ограничений.

## Правило перехода между этапами

Переход выполняется по проверяемым критериям выхода, а не только по факту написания кода. Если критическая проверка не пройдена, этап остаётся незавершённым. Пользовательские испытания Alpha собирают обратную связь для следующих этапов, но не заменяют автоматические тесты и аудит безопасности.
