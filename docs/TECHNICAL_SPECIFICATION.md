# RaskolZones — техническое задание и архитектурные решения

> Статус: проектирование, решения A-00–A-17 зафиксированы.
> Целевая платформа: Paper 26.2, Java 25.
> Репозиторий: hayferdahmer/RaskolZonez.
> Этот документ фиксирует согласованные требования. Он не означает, что функциональность уже реализована.

## 1. Назначение и границы проекта

RaskolZones — серверный плагин географии и территорий для Minecraft-сервера РАСКОЛ. Плагин предоставляет модель мира, геометрические территории, правила доступа, обнаружение мест, исследование, атлас, внутриигровой редактор и интеграции с другими серверными системами.

Целевая платформа — Paper 26.2 и Java 25. Клиентские модификации не требуются. Ядро должно работать без Towny, BlueMap, WorldEdit, WorldGuard и LuckPerms; интеграции подключаются через необязательные адаптеры.

Основные принципы:
- собственная географическая модель RaskolZones;
- чёткое разделение ядра и интеграционных адаптеров;
- безопасное разрешение конфликтов и запрет по умолчанию для неопределённых прав;
- отсутствие блокирующих операций хранения и тяжёлых вычислений на основном потоке;
- сохранность данных при выгрузке миров и отказах внешних интеграций;
- расширяемость без необходимости менять исходный код при добавлении пользовательских типов территорий.

## 2. Географическая модель и иерархия (A-00)

Выбрана гибридная архитектура с собственной моделью географии и движком территорий. WorldEdit может использоваться как необязательный инструмент выбора, импорта и экспорта. WorldGuard подключается через отдельный необязательный адаптер.

Иерархия:
1. Континент.
2. Королевство/государство.
3. Регион.
4. Локация/подзона.

В географии могут существовать города, деревни, подземелья, замки, арены, клановые территории, PvP-зоны, безопасные зоны, ресурсные и квестовые места, а также скрытые локации.

Core отвечает за географию, поиск территорий, уведомления, хранение, permissions и внутренний атлас. Интеграции не должны становиться обязательными зависимостями ядра.

## 3. Геометрия территорий (A-01)

Выбрана гибридная геометрическая модель:
- прямоугольные области;
- произвольные полигоны;
- вертикальные ограничения minY/maxY;
- составные территории и объединения;
- возможность представления отверстий;
- поддержка сложных пересечений и вложенности.

Редактор должен позволять создавать и изменять вершины и форму. Проверка валидности геометрии выполняется до сохранения; невалидная геометрия получает отдельное диагностическое состояние.

## 4. Permissions и разрешение прав (A-02, A-10)

Выбрана гибридная модель permissions:
- собственные роли и разрешения RaskolZones;
- интеграция с LuckPerms и использование глобальных групп/permissions;
- публичный API для проверки прав другими плагинами;
- опциональный адаптер Towny;
- раздельное представление территориальных прав, членства в городе и глобальных permissions.

Группа LuckPerms сама по себе не предоставляет доступ ко всем территориям определённого назначения: назначение в конкретную территорию/роль проверяется отдельно.

Политика разрешения:
- наследование прав настраивается по типам разрешений;
- дочерняя территория может переопределять права родителя;
- ALLOW/DENY разрешаются с учётом контекста действия, приоритета источника и специальных правил безопасности;
- RaskolZones — владелец прав для собственных территорий; Towny — источник данных для импортированных объектов; LuckPerms — источник глобальных групп и permissions;
- если право не определено, действие запрещено;
- ошибка интеграции не считается разрешением.

Требуется единый Permission Evaluation Service. Контекст проверки включает UUID игрока, мир, координаты, все применимые территории, роли, тип объекта и событие/действие.

## 5. Интеграция с Towny: синхронизация и владение данными (A-03, A-15)

Для каждого типа объекта задаётся собственный источник истины:
- Towny остаётся источником истины для импортированных городов, участков, владельцев и соответствующего членства;
- RaskolZones является источником истины для собственных объектов.

Изменения Towny автоматически обнаруживаются и синхронизируются с RaskolZones и представлениями BlueMap. Синхронизация должна корректно обрабатывать изменения, удаления и переименования, не создавать дубликаты. Для связи используются устойчивые внешние идентификаторы и таблица соответствий.

Выбранная глубина интеграции — hybrid:
- чтение и автоматическая синхронизация;
- запись в Towny только через отдельно разрешённые операции;
- импортируются города, нации, участки, жители, владельцы и типы участков;
- налоги/экономические параметры и аванпосты не входят в обязательный объём первой версии;
- удалённые во внешней системе объекты помечаются удалёнными, история и связи сохраняются; окончательное удаление выполняется по отдельной политике;
- членство и владельцы отслеживаются постоянно, включая историю значимых изменений;
- известные типы участков распознаются; неизвестные импортируются как общие с сохранением исходного идентификатора и возможностью администраторского сопоставления.

Towny-адаптер необязателен. Конкретные API и совместимость проверяются для выбранной версии Towny на этапе реализации.

## 6. Визуальный редактор территорий (A-04, A-13)

Редактор — центральная функция плагина. Команда `/zones editor` открывает его.

Обязательные возможности:
- живая подсветка границ и вершин;
- Undo/Redo;
- внутриигровой GUI управления;
- предварительный просмотр и синхронизация BlueMap;
- редактирование высоты Y;
- добавление, перемещение и удаление точек;
- копирование/клонирование территорий.

Изменения сначала существуют как черновик. Save фиксирует их, Cancel отбрасывает. WorldEdit — необязательное удобство. Редактор не изменяет блоки мира.

Для отображения используются частицы и Display Entities: частицы — для геометрии, Display Entities — для подписей, маркеров и вспомогательных элементов. Администратор получает подробную визуализацию в редакторе, обычные игроки — только настроенные игровые эффекты и уведомления.

Вершины редактируются интерактивными маркерами. Interaction Entities привязаны к сессии редактора и защищены от посторонних. Временные сущности очищаются при закрытии редактора, выходе игрока, отключении плагина и выгрузке мира. Для визуализации запрещено изменять реальные блоки. Предусматриваются дистанционная видимость, ограничение частоты обновлений, кэш геометрии и индивидуальные настройки редактора.

Используется Paper API; клиентские моды и обязательные packet hacks не допускаются.

## 7. Уведомления при входе (A-05)

Выбрана полностью настраиваемая система уведомлений. Поддерживаются:
- крупное название большой области;
- компактное уведомление о подзоне;
- отдельное уведомление о первом открытии;
- индивидуальные звуки территорий;
- описание и история места;
- опасность и рекомендуемый уровень;
- принадлежность фракции.

Для каждого типа территории настраиваются длительность анимации, цвета, текст, звук и условия показа. Первые открытия хранятся персонально. Необходимо предотвращать спам и корректно обрабатывать пересечения территорий.

## 8. Исследование мира и открытие территорий (A-06, A-16)

Модель discovery — hybrid:
- обычные территории открываются при входе;
- секретные места могут требовать квестов, точек исследования или других условий.

Неисследованные территории могут отображаться на карте визуально отличающимся образом; секреты не раскрываются до выполнения условий. Обязательны:
- персональный прогресс исследования;
- достижения исследования;
- события для внешних наград;
- секретные локации;
- личный атлас мира;
- процент изучения региона.

Групповое/совместное открытие не входит в обязательные требования без отдельного решения. Прогресс игрока хранится отдельно от географических данных; изменение границ не сбрасывает открытия.

Интеграция с RPG-системами — hybrid: собственное ядро исследования и API/адаптеры для внешних систем. События, которые должны предоставляться интеграциям:
- первое открытие территории;
- полное исследование региона;
- обнаружение секретной локации;
- посещение важных ориентиров.

Модель наград — external: RaskolZones публикует события и контекст, а награды выдаются внешними плагинами через API. Прогресс исследования — hybrid: открытия, проценты изучения, история, достижения и статистика. Секретные места — hybrid: обычные открываются исследованием, особые требуют дополнительных условий.

События должны иметь устойчивые идентификаторы и механизм защиты от повторной обработки, чтобы повторные входы, retries или перезапуски не приводили к повторной выдаче наград внешними системами.

## 9. Атлас (A-07)

Выбран гибридный атлас: интерактивная карта, иерархический просмотр, журнал исследования и карточки территорий.

Способы доступа:
- команда `/atlas`;
- предмет «Книга атласа»;
- BlueMap через адаптер.

Карточки содержат описание регионов, поселения, подземелья и особые локации, статус и процент исследования, опасность и рекомендуемый уровень, контролирующую фракцию.

Решение рассчитано на Paper 26.2: клиентские модификации не требуются. BlueMap — необязательная интеграция.

## 10. Типы территорий (A-08)

Выбрана гибридная система: встроенные типы плюс пользовательские.

Встроенные типы:
`continent`, `kingdom`, `region`, `city`, `village`, `dungeon`, `castle`, `arena`, `pvp`, `pve`, `safe`, `resource`, `quest`, `clan`.

Пользовательские типы создаются только администраторами с соответствующим permission. Тип является расширяемым профилем территории и определяет категорию атласа, визуальное оформление, уведомления и применимые правила. Добавление нового типа не должно требовать изменения исходников.

## 11. Пересечения, приоритеты и конфликты (A-09)

Вложенность и частичные пересечения разрешены, ограничения задаются по типам территорий.

Приоритет определяется гибридно:
- иерархией;
- числовым весом;
- специфичностью;
- отдельными правилами для конкретной механики.

Для PvP, PvE, строительства, взаимодействий, уведомлений и permissions задаются отдельные политики разрешения конфликтов. Неоднозначные конфликты разрешаются безопасно, без случайного предоставления доступа.

## 12. Хранение, миграции и резервное копирование (A-11)

Выбрано гибридное хранилище:
- SQLite по умолчанию;
- MySQL и PostgreSQL через подключаемые реализации;
- единый интерфейс доступа к данным.

Предусматриваются автоматические резервные копии по расписанию, ручной запуск, контроль целостности и восстановление выбранной копии.

Миграции автоматические и версионированные, с предварительной проверкой и резервной копией. Ошибка миграции не должна оставлять базу в частично обновлённом состоянии. Нужны экспорт и восстановление данных.

Первая версия рассчитана на один сервер, но архитектура должна допускать будущую многосерверность. Межсерверная синхронизация в первой версии не требуется. Операции хранения не должны блокировать главный поток Paper.

## 13. Многомировая модель (A-12)

География каждого мира независима, системные настройки могут быть общими, а логические связи и маршруты между мирами поддерживаются отдельно.

Основной идентификатор мира — UUID; имя используется для отображения и диагностики. Загрузка и выгрузка миров обнаруживаются автоматически. Опасные административные операции требуют подтверждения.

Поддерживаются логические маршруты, порталы, точки телепортации и будущие способы перемещения через API. Если мир недоступен, данные территорий сохраняются без изменений, пространственные проверки временно не выполняются, работа восстанавливается при загрузке мира. Недоступность мира нельзя трактовать как удаление или изменение состояния территории.

## 14. BlueMap (A-14)

BlueMap — слой представления, а не источник истины. Адаптер необязателен; без него продолжают работать ядро, команды, геометрия и внутриигровой атлас.

Синхронизация — hybrid:
- изменения RaskolZones и Towny автоматически публикуются;
- внешние изменения не перезаписывают исходную географию без подтверждения;
- публичные территории видны всем;
- секретные и скрытые места защищены политикой discovery/access.

Обязательные слои:
`boundaries`, `labels`, `hierarchy`, `danger`, `faction`, `locations`.

Ошибки BlueMap не блокируют core. Нужны очередь изменений, повторные попытки, журнал ошибок и уведомление администратора. Важные изменения публикуются оперативно, массовые — пакетно. После перезапуска и повторной синхронизации маркеры восстанавливаются без дублирования.

## 15. Производительность и конкурентность (A-17)

Все решения A-17 — hybrid.

### 15.1 Пространственная индексация
Использовать комбинированные пространственные индексы с учётом масштаба и геометрии объектов. Индекс должен быстро отбирать кандидатов, после чего выполняется точная геометрическая проверка. Конкретные структуры данных выбираются и сравниваются на этапе реализации и нагрузочного тестирования.

### 15.2 Обнаружение пересечений при перемещении
Использовать оптимизированную обработку событий перемещения с порогами и пространственными ячейками. Быстрые перемещения, телепортации, переходы между мирами и пересечение узких границ не должны приводить к пропуску входа или выхода. Проверки должны учитывать фактическую траекторию/конечное состояние там, где это необходимо.

### 15.3 Кэширование
Кэшировать геометрию, результаты пространственных запросов, активные территории игроков и контекстные результаты. Применять версионирование данных и точечную инвалидацию после изменений, чтобы устаревшие результаты не влияли на permissions и игровые правила.

### 15.4 Асинхронная обработка
Тяжёлые вычисления выполнять вне основного потока на неизменяемых снимках данных. Вызовы Bukkit/Paper API и игровые действия выполнять только на допустимом потоке. Обеспечить безопасную диспетчеризацию результатов и проверку актуальности снимка до применения.

### 15.5 Массовые изменения
Критические изменения обрабатывать немедленно. Массовые импорты, перестроение индексов и пакетные обновления выполнять пакетно с ограничением нагрузки и отслеживаемым прогрессом.

### 15.6 Высокая нагрузка
Использовать адаптивное снижение частоты или объёма второстепенных вычислений. Нельзя ради производительности пропускать критические проверки, ошибочно разрешать запрещённое действие или терять обязательные события. Предусмотреть метрики и диагностику для выявления узких мест.

## 16. Неподтверждённые детали и правила реализации

Следующие решения требуют конкретизации в последующих этапах проектирования и/или проверки на выбранных версиях зависимостей:
- точные структуры пространственных индексов и критерии выбора между ними;
- численные пороги обработки перемещений и ограничения очередей;
- точная схема таблиц и индексов хранилища;
- контракты публичного API и событий;
- точные API Paper 26.2, Towny, BlueMap, LuckPerms, WorldEdit и WorldGuard;
- численные лимиты производительности, определяемые нагрузочными тестами.

Ни один адаптер не должен быть обязательной зависимостью ядра. Ошибка внешнего адаптера не должна приводить к fail-open для прав или к потере собственных данных RaskolZones.
