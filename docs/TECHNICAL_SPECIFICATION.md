# RaskolZones — техническое задание и архитектурные решения

> Статус: реализация инженерного фундамента. Канонический журнал архитектурных решений содержит A-00–A-43; этот документ является синхронизируемой технической спецификацией.
> Целевая платформа: Paper 26.2, Java 25.
> Репозиторий: hayferdahmer/RaskolZonez.
> Этот документ фиксирует согласованные требования. Он не означает, что функциональность уже реализована.

## 1. Назначение и границы проекта

RaskolZones — серверный плагин географии и территорий для Minecraft-сервера РАСКОЛ. Плагин предоставляет модель мира, геометрические территории, правила доступа, обнаружение мест, исследование, атлас, внутриигровой редактор и интеграции с другими серверными системами.

Целевая платформа — Paper 26.2 и Java 25. Клиентские модификации не требуются. Ядро должно работать без Towny, BlueMap, WorldEdit, WorldGuard и LuckPerms; интеграции подключаются через необязательные адаптеры.

Основные принципы:
- собственная географическая модель RaskolZones;
- чёткое разделение ядра и интеграционных адаптеров;
- безопасное разрешение конфликтов и запрет по умолчанию для неопределённых прав;
- отсутствие блокирующих операций хранения и тяжёлых вычислений на основном потоке;
- сохранность данных при выгрузке миров и отказах внешних интеграций;
- расширяемость без необходимости менять исходный код при добавлении пользовательских типов территорий.

## 2. Географическая модель и иерархия (A-00)

Выбрана гибридная архитектура с собственной моделью географии и движком территорий. WorldEdit может использоваться как необязательный инструмент выбора, импорта и экспорта. WorldGuard подключается через отдельный необязательный адаптер.

Иерархия:
1. Континент.
2. Королевство/государство.
3. Регион.
4. Локация/подзона.

В географии могут существовать города, деревни, подземелья, замки, арены, клановые территории, PvP-зоны, безопасные зоны, ресурсные и квестовые места, а также скрытые локации.

Core отвечает за географию, поиск территорий, уведомления, хранение, permissions и внутренний атлас. Интеграции не должны становиться обязательными зависимостями ядра.

## 3. Геометрия территорий (A-01)

Выбрана гибридная геометрическая модель:
- прямоугольные области;
- произвольные полигоны;
- вертикальные ограничения minY/maxY;
- составные территории и объединения;
- возможность представления отверстий;
- поддержка сложных пересечений и вложенности.

Редактор должен позволять создавать и изменять вершины и форму. Проверка валидности геометрии выполняется до сохранения; невалидная геометрия получает отдельное диагностическое состояние.

## 4. Permissions и разрешение прав (A-02, A-10)

Выбрана гибридная модель permissions:
- собственные роли и разрешения RaskolZones;
- интеграция с LuckPerms и использование глобальных групп/permissions;
- публичный API для проверки прав другими плагинами;
- опциональный адаптер Towny;
- раздельное представление территориальных прав, членства в городе и глобальных permissions.

Группа LuckPerms сама по себе не предоставляет доступ ко всем территориям определённого назначения: назначение в конкретную территорию/роль проверяется отдельно.

Политика разрешения:
- наследование прав настраивается по типам разрешений;
- дочерняя территория может переопределять права родителя;
- ALLOW/DENY разрешаются с учётом контекста действия, приоритета источника и специальных правил безопасности;
- RaskolZones — владелец прав для собственных территорий; Towny — источник данных для импортированных объектов; LuckPerms — источник глобальных групп и permissions;
- если право не определено, действие запрещено;
- ошибка интеграции не считается разрешением.

Требуется единый Permission Evaluation Service. Контекст проверки включает UUID игрока, мир, координаты, все применимые территории, роли, тип объекта и событие/действие.

## 5. Интеграция с Towny: синхронизация и владение данными (A-03, A-15)

Для каждого типа объекта задаётся собственный источник истины:
- Towny остаётся источником истины для импортированных городов, участков, владельцев и соответствующего членства;
- RaskolZones является источником истины для собственных объектов.

Изменения Towny автоматически обнаруживаются и синхронизируются с RaskolZones и представлениями BlueMap. Синхронизация должна корректно обрабатывать изменения, удаления и переименования, не создавать дубликаты. Для связи используются устойчивые внешние идентификаторы и таблица соответствий.

Выбранная глубина интеграции — hybrid:
- чтение и автоматическая синхронизация;
- запись в Towny только через отдельно разрешённые операции;
- импортируются города, нации, участки, жители, владельцы и типы участков;
- налоги/экономические параметры и аванпосты не входят в обязательный объём первой версии;
- удалённые во внешней системе объекты помечаются удалёнными, история и связи сохраняются; окончательное удаление выполняется по отдельной политике;
- членство и владельцы отслеживаются постоянно, включая историю значимых изменений;
- известные типы участков распознаются; неизвестные импортируются как общие с сохранением исходного идентификатора и возможностью администраторского сопоставления.

Towny-адаптер необязателен. Конкретные API и совместимость проверяются для выбранной версии Towny на этапе реализации.

## 6. Визуальный редактор территорий (A-04, A-13)

Редактор — центральная функция плагина. Команда `/zones editor` открывает его.

Обязательные возможности:
- живая подсветка границ и вершин;
- Undo/Redo;
- внутриигровой GUI управления;
- предварительный просмотр и синхронизация BlueMap;
- редактирование высоты Y;
- добавление, перемещение и удаление точек;
- копирование/клонирование территорий.

Изменения сначала существуют как черновик. Save фиксирует их, Cancel отбрасывает. WorldEdit — необязательное удобство. Редактор не изменяет блоки мира.

Для отображения используются частицы и Display Entities: частицы — для геометрии, Display Entities — для подписей, маркеров и вспомогательных элементов. Администратор получает подробную визуализацию в редакторе, обычные игроки — только настроенные игровые эффекты и уведомления.

Вершины редактируются интерактивными маркерами. Interaction Entities привязаны к сессии редактора и защищены от посторонних. Временные сущности очищаются при закрытии редактора, выходе игрока, отключении плагина и выгрузке мира. Для визуализации запрещено изменять реальные блоки. Предусматриваются дистанционная видимость, ограничение частоты обновлений, кэш геометрии и индивидуальные настройки редактора.

Используется Paper API; клиентские моды и обязательные packet hacks не допускаются.

## 7. Уведомления при входе (A-05)

Выбрана полностью настраиваемая система уведомлений. Поддерживаются:
- крупное название большой области;
- компактное уведомление о подзоне;
- отдельное уведомление о первом открытии;
- индивидуальные звуки территорий;
- описание и история места;
- опасность и рекомендуемый уровень;
- принадлежность фракции.

Для каждого типа территории настраиваются длительность анимации, цвета, текст, звук и условия показа. Первые открытия хранятся персонально. Необходимо предотвращать спам и корректно обрабатывать пересечения территорий.

## 8. Исследование мира и открытие территорий (A-06, A-16)

Модель discovery — hybrid:
- обычные территории открываются при входе;
- секретные места могут требовать квестов, точек исследования или других условий.

Неисследованные территории могут отображаться на карте визуально отличающимся образом; секреты не раскрываются до выполнения условий. Обязательны:
- персональный прогресс исследования;
- достижения исследования;
- события для внешних наград;
- секретные локации;
- личный атлас мира;
- процент изучения региона.

Групповое/совместное открытие не входит в обязательные требования без отдельного решения. Прогресс игрока хранится отдельно от географических данных; изменение границ не сбрасывает открытия.

Интеграция с RPG-системами — hybrid: собственное ядро исследования и API/адаптеры для внешних систем. События, которые должны предоставляться интеграциям:
- первое открытие территории;
- полное исследование региона;
- обнаружение секретной локации;
- посещение важных ориентиров.

Модель наград — external: RaskolZones публикует события и контекст, а награды выдаются внешними плагинами через API. Прогресс исследования — hybrid: открытия, проценты изучения, история, достижения и статистика. Секретные места — hybrid: обычные открываются исследованием, особые требуют дополнительных условий.

События должны иметь устойчивые идентификаторы и механизм защиты от повторной обработки, чтобы повторные входы, retries или перезапуски не приводили к повторной выдаче наград внешними системами.

## 9. Атлас (A-07)

Выбран гибридный атлас: интерактивная карта, иерархический просмотр, журнал исследования и карточки территорий.

Способы доступа:
- команда `/atlas`;
- предмет «Книга атласа»;
- BlueMap через адаптер.

Карточки содержат описание регионов, поселения, подземелья и особые локации, статус и процент исследования, опасность и рекомендуемый уровень, контролирующую фракцию.

Решение рассчитано на Paper 26.2: клиентские модификации не требуются. BlueMap — необязательная интеграция.

## 10. Типы территорий (A-08)

Выбрана гибридная система: встроенные типы плюс пользовательские.

Встроенные типы:
`continent`, `kingdom`, `region`, `city`, `village`, `dungeon`, `castle`, `arena`, `pvp`, `pve`, `safe`, `resource`, `quest`, `clan`.

Пользовательские типы создаются только администраторами с соответствующим permission. Тип является расширяемым профилем территории и определяет категорию атласа, визуальное оформление, уведомления и применимые правила. Добавление нового типа не должно требовать изменения исходников.

## 11. Пересечения, приоритеты и конфликты (A-09)

Вложенность и частичные пересечения разрешены, ограничения задаются по типам территорий.

Приоритет определяется гибридно:
- иерархией;
- числовым весом;
- специфичностью;
- отдельными правилами для конкретной механики.

Для PvP, PvE, строительства, взаимодействий, уведомлений и permissions задаются отдельные политики разрешения конфликтов. Неоднозначные конфликты разрешаются безопасно, без случайного предоставления доступа.

## 12. Хранение, миграции и резервное копирование (A-11)

Выбрано гибридное хранилище:
- SQLite по умолчанию;
- MySQL и PostgreSQL через подключаемые реализации;
- единый интерфейс доступа к данным.

Предусматриваются автоматические резервные копии по расписанию, ручной запуск, контроль целостности и восстановление выбранной копии.

Миграции автоматические и версионированные, с предварительной проверкой и резервной копией. Ошибка миграции не должна оставлять базу в частично обновлённом состоянии. Нужны экспорт и восстановление данных.

Первая версия рассчитана на один сервер, но архитектура должна допускать будущую многосерверность. Межсерверная синхронизация в первой версии не требуется. Операции хранения не должны блокировать главный поток Paper.

## 13. Многомировая модель (A-12)

География каждого мира независима, системные настройки могут быть общими, а логические связи и маршруты между мирами поддерживаются отдельно.

Основной идентификатор мира — UUID; имя используется для отображения и диагностики. Загрузка и выгрузка миров обнаруживаются автоматически. Опасные административные операции требуют подтверждения.

Поддерживаются логические маршруты, порталы, точки телепортации и будущие способы перемещения через API. Если мир недоступен, данные территорий сохраняются без изменений, пространственные проверки временно не выполняются, работа восстанавливается при загрузке мира. Недоступность мира нельзя трактовать как удаление или изменение состояния территории.

### Реализация World Registry

Реестр миров использует UUID как единственный стабильный идентификатор; имя хранится только как изменяемое отображаемое поле. Реестр содержит время первого и последнего обнаружения и состояние `LOADED` / `UNLOADED`. При старте плагин регистрирует все уже загруженные Paper-миры, а события `WorldLoadEvent` и `WorldUnloadEvent` обновляют состояние автоматически. Выгрузка не удаляет запись. Повторная загрузка того же UUID восстанавливает состояние существующей записи и сохраняет время первого обнаружения.

Схема SQLite обновлена миграцией v2 (`world_registry`). Все операции реестра выполняются через асинхронный storage-интерфейс и последовательный SQLite executor; Bukkit/Paper объекты не передаются в фоновый слой. Реестр предоставляет внутренние операции регистрации, выгрузки, поиска и перечисления. Это фундаментальная инфраструктура, а не пользовательская команда или законченная система географии.

## 14. BlueMap (A-14)

BlueMap — слой представления, а не источник истины. Адаптер необязателен; без него продолжают работать ядро, команды, геометрия и внутриигровой атлас.

Синхронизация — hybrid:
- изменения RaskolZones и Towny автоматически публикуются;
- внешние изменения не перезаписывают исходную географию без подтверждения;
- публичные территории видны всем;
- секретные и скрытые места защищены политикой discovery/access.

Обязательные слои:
`boundaries`, `labels`, `hierarchy`, `danger`, `faction`, `locations`.

Ошибки BlueMap не блокируют core. Нужны очередь изменений, повторные попытки, журнал ошибок и уведомление администратора. Важные изменения публикуются оперативно, массовые — пакетно. После перезапуска и повторной синхронизации маркеры восстанавливаются без дублирования.

## 15. Производительность и конкурентность (A-17)

Все решения A-17 — hybrid.

### 15.1 Пространственная индексация
Использовать комбинированные пространственные индексы с учётом масштаба и геометрии объектов. Индекс должен быстро отбирать кандидатов, после чего выполняется точная геометрическая проверка. Конкретные структуры данных выбираются и сравниваются на этапе реализации и нагрузочного тестирования.

### 15.2 Обнаружение пересечений при перемещении
Использовать оптимизированную обработку событий перемещения с порогами и пространственными ячейками. Быстрые перемещения, телепортации, переходы между мирами и пересечение узких границ не должны приводить к пропуску входа или выхода. Проверки должны учитывать фактическую траекторию/конечное состояние там, где это необходимо.

### 15.3 Кэширование
Кэшировать геометрию, результаты пространственных запросов, активные территории игроков и контекстные результаты. Применять версионирование данных и точечную инвалидацию после изменений, чтобы устаревшие результаты не влияли на permissions и игровые правила.

### 15.4 Асинхронная обработка
Тяжёлые вычисления выполнять вне основного потока на неизменяемых снимках данных. Вызовы Bukkit/Paper API и игровые действия выполнять только на допустимом потоке. Обеспечить безопасную диспетчеризацию результатов и проверку актуальности снимка до применения.

### 15.5 Массовые изменения
Критические изменения обрабатывать немедленно. Массовые импорты, перестроение индексов и пакетные обновления выполнять пакетно с ограничением нагрузки и отслеживаемым прогрессом.

### 15.6 Высокая нагрузка
Использовать адаптивное снижение частоты или объёма второстепенных вычислений. Нельзя ради производительности пропускать критические проверки, ошибочно разрешать запрещённое действие или терять обязательные события. Предусмотреть метрики и диагностику для выявления узких мест.

## 16. Сквозные архитектурные требования A-18–A-43

### A-18. Публичный API и интеграционные контракты
- Публичный Java API, Paper events и versioned integration contracts отделены от внутренних классов и схем хранения.
- API и контракты имеют явную версию, правила SemVer/deprecation, документированные thread semantics, timing, cancellability и допустимые операции.
- Ожидаемые domain errors возвращаются через Result-подобные типы с машинно-читаемыми кодами; неожиданные сбои не маскируются.
- Проверка permissions выполняется контекстно и fail-closed.

### A-19. Безопасность административных операций
- Значимые административные действия журналируются структурированно с actor, action, object, time, context, result и correlation ID; секреты не попадают в аудит.
- Подтверждения зависят от риска, масштаба и обратимости; критические операции могут требовать второго подтверждения и preview.
- Редакторские сессии используют владельца, ID, TTL, состояние, проверку версии и безопасное освобождение.
- Интеграционные полномочия разделены по операциям; break-glass — ограниченный по времени, обоснованный и полностью аудируемый механизм.

### A-20. Команды, GUI и конфигурация
- Команды и GUI предоставляют разные, но согласованные интерфейсы; команды сохраняются для точных и автоматизируемых операций.
- Конфигурация разделена по подсистемам, версионируется и проверяется по схеме.
- Reload выполняется через validate/prepare/atomic apply; ошибочная конфигурация не должна частично менять состояние или ослаблять безопасность.
- Русский язык — базовый; предусмотрены английский и пользовательские языковые пакеты с fallback.
- GUI не является границей безопасности: права и состояние перепроверяются сервером при выполнении действия.

### A-21. Жизненный цикл и отказоустойчивость
- Startup staged: обязательные зависимости и readiness gates проверяются до активации зависимых функций.
- Shutdown прекращает новые операции, завершает безопасные задачи, сохраняет состояние и очищает ресурсы в обратном порядке зависимостей с timeout.
- Отказы изолируются; необязательные адаптеры могут перейти в degraded/unavailable без отключения core.
- Восстановление использует ограниченные retries/backoff, идемпотентность, аудит и ручное подтверждение для опасных действий.
- Health статусы: healthy, degraded, unavailable, failed; метрики и диагностика не раскрывают чувствительные данные.

### A-22. Данные, миграции и совместимость форматов
- Миграции версионированы, последовательны, идемпотентны, имеют preflight, backup, preconditions/postconditions и проверку результата.
- Rollback выполняется только там, где он безопасен и подтверждён; необратимые преобразования не объявляются обратимыми.
- Схема данных версионируется независимо от версии плагина; неизвестные обязательные структуры отклоняются диагностируемо.
- Export/import использует версионированный JSON для обмена и YAML для редактируемых конфигураций, с preview и подтверждением.
- Retention задаётся по категориям; важная история архивируется до контролируемого окончательного удаления.

### A-23. Игровые правила и события Paper
- Специализированные Paper listeners направляют события в общий движок территориальных правил; бизнес-логика находится в тестируемых сервисах.
- PvP, PvE, строительство и взаимодействия имеют раздельные политики и учитывают инициатора, цель, источник эффекта и затронутые территории.
- Обрабатываются косвенные эффекты в пределах возможностей Paper API: снаряды, взрывы, жидкости, огонь, поршни, механизмы и другие поддерживаемые события.
- Конфликты с другими плагинами разрешаются явными политиками и адаптерами; RaskolZones не обещает безусловно переопределять чужие плагины.

### A-24. Перемещения и переходы территорий
- Определение переходов использует Paper movement events, пространственные индексы и дополнительные проверки итогового состояния.
- Учитываются конечные позиции и траектории там, где это нужно для узких границ и быстрых перемещений.
- Телепортации, порталы и смена миров обрабатываются специализированно.
- Порядок переходов учитывает иерархию, приоритет, специфичность и тип перехода; дедупликация защищает от повторной обработки без потери реальных переходов.

### A-25. Discovery и персональное исследование
- Обычные территории открываются входом; секретные могут требовать условий, квестов или специальных точек.
- Видимость определяется типом, секретностью, доступом и прогрессом; скрытая информация не раскрывается преждевременно.
- Персональный прогресс включает открытия, посещения, ориентиры, секреты, достижения и процент исследования.
- Уведомления настраиваются по событиям, типам территорий и пользовательскому прогрессу; история открытий сохраняется.

### A-26. Владение и членство
- Поддерживаются модели владения игроком, группой, кланом, городом, государством и системным владельцем.
- Роли, участники, приглашения и временное членство имеют явные состояния и права.
- Передача владения требует подтверждения получателя; критические территории используют усиленные процедуры.
- Lifecycle включает создание, активность, приостановку, архивирование, восстановление и окончательное удаление с проверками и аудитом.
- Бесхозные территории получают явный статус и временную политику.

### A-27. Политики мира
- Отдельные контекстные политики регулируют погоду/время, взрывы/огонь, жидкости/физические эффекты, Redstone, сущности и транспорт.
- При оценке учитываются источник, инициатор, траектория, затронутые территории, принадлежность сущностей и тип действия.
- Неопределённость разрешается безопасно; гарантии ограничены теми эффектами, которые Paper API позволяет надёжно контролировать.

### A-28. Внешние интеграции и адаптеры
- Адаптеры используют versioned contracts, capability detection и минимально необходимые полномочия.
- Для каждого набора данных определён источник истины; чтение, запись и синхронизация контролируются отдельно.
- Отказы изолируются, retries ограничены, деградация диагностируется; ошибки защищённых операций не открывают доступ.
- Плагины работают в общей JVM, поэтому контрактная проверка не является sandbox и не обеспечивает абсолютную изоляцию от вредоносного кода.

### A-29. Администрирование и наблюдаемость
- Предусмотрены GUI/команды диагностики, health по core/модулям/адаптерам, метрики, structured logs и correlation IDs.
- Alerts имеют severity, правила дедупликации и группировки; диагностические пакеты проходят sanitization.
- Обслуживание автоматически выполняется только для безопасных операций; рискованные требуют preview и подтверждения.
- Права на просмотр, диагностику и изменение разделены и аудируются.

### A-30. Совместимость и выпуск
- Базовая платформа — Paper 26.2 + Java 25; поддерживаемые диапазоны версий публикуются и проверяются.
- Проверки включают unit, integration, Paper scenarios, нагрузочные, регрессионные и ручные smoke tests.
- Стадии выпуска: development, alpha, beta, RC, stable; Stable требует ручного подтверждения.
- Обновление включает проверку совместимости, backup, preflight и безопасный перезапуск; откат JAR и схемы рассматривается отдельно.
- Релизные артефакты имеют контроль целостности и воспроизводимую процедуру проверки.

### A-31. Производительность и масштабирование
- Задаются профили малых, средних и крупных серверов; unlimited не обещается.
- Для критических пространственных запросов и операций устанавливаются измеряемые бюджеты.
- Кэши ограничены по размеру и имеют eviction; очереди и конкурентность bounded.
- При перегрузке второстепенные функции деградируют адаптивно, но permissions и критические правила сохраняются.
- CI использует benchmarks, scale tests, profiling и сравнение регрессий.

### A-32. Критерии готовности и приёмки
- Приёмка включает checklist требований, позитивные и негативные сценарии и измеримые критерии результата.
- Процент покрытия дополняется обязательным набором критических тестов.
- Critical/high security defects блокируют Stable, кроме документированных и утверждённых исключений.
- Совместимость и производительность подтверждаются матрицей и воспроизводимыми тестами.
- Stable требует CI gates, отсутствия блокирующих дефектов, проверенных миграций и ручного approval.
- Первый Stable включает завершённые Core и основные модули; заглушки не считаются готовой функцией.

### A-33. Модульные границы и трассируемость
- Архитектура модульная; модули не обязаны быть отдельными JAR/Paper plugins.
- Зависимости направлены через контракты; домен не зависит от инфраструктуры, циклы запрещены.
- У каждого доменного набора данных есть единственный авторитетный владелец; прямое изменение чужого storage запрещено.
- Трассируемость сквозная: requirement ID → decisions → modules/contracts → tests → acceptance criteria.
- Межмодульные процессы имеют coordinator, этапы, идемпотентность, прогресс и компенсации; внешние эффекты не обещают глобальный rollback.

### A-34. Согласованность и восстановление данных
- Конкурентные изменения используют optimistic locking и контролируемые блокировки; silent overwrite запрещён.
- Атомарность обеспечивается транзакциями там, где возможно, и управляемыми workflow для межсистемных процессов.
- Повторы защищены durable idempotency и dedup; exactly-once delivery не обещается.
- Связанные записи сохраняют порядок и checkpoints; после сбоя выполняются проверка состояния и безопасное продолжение/компенсация.
- Integrity checks выполняются при записи, старте и периодически; автоматическое исправление допускается только для однозначно безопасных случаев.
- Конфликты источников решаются владельцем данных и явными политиками, не last-write-wins.

### A-35. Модель угроз и границы доверия
- Формальная модель угроз включает активы, нарушителей, поверхности атаки, последствия, меры защиты и остаточные риски; рассматриваются практические сценарии атак на Paper-плагин.
- Недоверенные входы проходят валидацию, контекстные лимиты и безопасную обработку.
- Межмодульные/адаптерные контракты проверяются; полномочия минимальны, чувствительные операции аудируются.
- Секреты хранятся во внешнем хранилище при наличии либо в защищённой локальной конфигурации; секреты не попадают в JAR, репозиторий и логи.
- Supply chain защищается dependency scanning, SBOM, подписью и provenance.
- Уязвимости обрабатываются по формальной политике с приоритетами, сроками и аудитом исправлений.
- Защита от resource abuse использует контекстные и глобальные лимиты, bounded queues/concurrency, backpressure и диагностику.

### A-37. Детерминированное разрешение территориальных правил
- Единая формальная матрица приоритетов задаёт фиксированный порядок сравнения; одинаковый контекст и набор правил всегда дают одинаковый результат.
- Обязательные ограничения безопасности оцениваются первыми и не отменяются обычным ALLOW. Далее применяются иерархия территории, числовой вес, специфичность, авторитетность источника и заранее определённые tie-breakers.
- Точная семантика уровней, направления сравнения весов и полный порядок критериев должны быть специфицированы и покрыты граничными тестами; неявный порядок обхода коллекций запрещён.
- При равенстве всех предшествующих критериев DENY побеждает ALLOW.
- Неполный обязательный контекст или недоступный авторитетный источник приводят к fail-closed отказу с машинно-читаемой причиной.
- Для результата формируется структурированный decision trace: применённые правила, источники, приоритеты, отклонённые варианты и итоговая причина; чувствительные данные и секретные сведения не раскрываются.
- Единый движок использует отдельные профили/стратегии для PvP, PvE, строительства, взаимодействий и иных категорий, сохраняя общие инварианты оценки, безопасности и трассировки.

### A-38. Точная семантика приоритетов
- Глобальный порядок сравнения: обязательная безопасность → иерархия территории → числовой вес → специфичность правила → авторитетность источника → стабильный tie-breaker. Каждый критерий применяется только при равенстве предыдущих.
- При отношении предок–потомок приоритет имеет дочерняя территория; геометрическое пересечение без связи в иерархии не считается родством. Для несвязанных территорий критерий иерархии равен.
- При равенстве иерархии побеждает больший валидированный числовой вес; далее — более специфичное правило с более узкой областью применимости и точными условиями.
- Авторитетность определяется централизованным реестром фиксированных уровней доверия. Неизвестный/непроверенный обязательный источник приводит к fail-closed; адаптер не может сам назначить себе уровень доверия.
- Финальный tie-breaker использует неизменяемые нормализованные ID правила и территории, сравниваемые лексикографически в фиксированном порядке. Runtime identity, случайные UUID и порядок коллекций запрещены.
- DENY-on-tie из A-37 имеет приоритет над ID tie-breaker: при равенстве семантических критериев DENY побеждает ALLOW; стабильные ID разрешают только остаточные ничьи между кандидатами с одинаковым эффектом.
- Одна и та же матрица применяется глобально ко всем категориям; категориальные профили не могут переставлять критерии или ослаблять безопасность.
- Матрица, реестр доверия и алгоритмы специфичности/нормализации должны иметь формальные контракты и граничные/регрессионные тесты.

### A-39. Актуальность контекста и атомарность применения правил
- Решение об ALLOW/DENY использует срок действия `version_bound` и привязано к версиям всех использованных данных (`version_bound`); изменение любой обязательной версии делает результат непригодным для применения.
- Контекст использует гибридное версионирование: глобальное поколение плюс точечные версии территорий, политик, членства, источников и иных зависимостей.
- Синхронное действие в исходном событии использует актуальную проверку; отложенное/асинхронное действие обязано проверить версии и пересчитать решение при устаревании.
- Проверка и применение защищены короткой сериализацией по цели и optimistic version check непосредственно перед эффектом. Конфликт версий не разрешается использованием старого ALLOW.
- При устаревшем контексте выполняются ограниченные повторы; после исчерпания лимита, повторной нестабильности или недоступности обязательного контекста применяется fail-closed.
- Локальные версии изменяются в той же границе фиксации данных; распространение уведомлений и инвалидация вторичных кэшей асинхронны. Неподтверждённый вторичный снимок не может разрешить защищённое действие.
- Неизменяемая decision receipt связывает субъект, действие, цель, эффект решения, версии, ID правил, область применимости и correlation ID. Исполнитель проверяет её актуальность непосредственно перед применением.
- Аудит различает вычисленное решение и фактический исход действия. Все повторы, конфликты версий и отказы наблюдаемы и ограничены по ресурсам.

### A-40. Защита квитанций решений от повторного и подменённого исполнения
- Квитанция одноразовая (`single`); повторная доставка идентифицируется стабильным operation ID и дедуплицируется как та же операция, а не новое разрешение.
- Квитанция полностью привязана к субъекту, действию, цели, канонизированным параметрам, миру и контексту. Изменение любого значимого поля делает её неприменимой.
- Подлинность и целостность подтверждаются серверной криптографической подписью или MAC с защищённым ключом. Проверка подписи не заменяет проверку статуса, одноразовости и актуальности версий A-39.
- Одноразовость обеспечивается долговременным реестром операций, атомарным claim и дедупликацией; оперативный кэш не является источником истины.
- До эффекта выполняется атомарный claim; затем фиксируется результат. Состояния issued → claimed → applied/failed/reconciliation-required имеют явные переходы, lease/fencing и устойчивый operation ID.
- После неопределённого результата выполняется reconciliation фактического эффекта. Повтор разрешён только при доказанном отсутствии эффекта и безопасной идемпотентности; неоднозначные операции не повторяются автоматически.
- Оперативный кэш сочетается с долговременным хранением критичных операций и аудиторских переходов. Retention, ротация ключей, доступ к аудиту и защита секретов формализуются.

### A-41. Управление жизненным циклом криптографических ключей
- Плановая ротация (`overlap`): новый ключ выпускает подписи, предыдущий остаётся verify-only на ограниченное окно; каждая квитанция содержит Key ID/версию.
- Квитанции старого ключа (`valid_until`) действуют до собственного срока истечения только пока ключ не отозван и проверки A-39/A-40 успешны. Отзыв блокирует исполнение немедленно.
- При компрометации (`revoke_fail_closed`) ключ немедленно отзывается, новые подписи запрещаются, связанные квитанции блокируются; незавершённые операции направляются на сверку.
- Хранение (`external_hsm`): внешний Vault/HSM при наличии, иначе защищённое локальное хранилище. Секреты не включаются в JAR, открытые конфиги, логи и диагностические пакеты.
- Распространение отзыва (`hybrid`): событие для оперативной доставки плюс проверка актуального реестра перед исполнением. Устаревший статус означает fail-closed; старые события не отменяют новый отзыв.
- Восстановление (`recovery`) требует независимого подтверждения, проверки целостности и аудита. Скомпрометированный ключ не возвращается в доверенное состояние; выпускается новый ключ с новым Key ID.
- Срок жизни (`risk_based`) определяется назначением, критичностью, интенсивностью использования и угрозами; задаются максимальный срок, окно перекрытия и основания внеплановой ротации.

### A-42. Криптографический профиль и цепочка доверия
- Основной алгоритм подписи — Ed25519 (`ed25519_agile`) с версионируемым профилем и контролируемой миграцией; неизвестные алгоритмы и автоматический downgrade запрещены.
- Ключи разделены по назначению (`separate`): квитанции, реестр доверия и служебные операции. Реестр ограничивает назначение каждого Key ID.
- Начальный корень доверия закреплён offline (`offline_pinned`); его замена требует независимого подтверждения и аудита.
- Реестр ключей (`signed_monotonic`) подписан, содержит монотонную версию; откат версии, нарушение подписи или цепочки доверия отклоняются.
- Защита downgrade (`strict_no_downgrade`): переход профиля только через явную версионированную миграцию.
- Подписываемые данные (`canonical_versioned`) детерминированно канонизируются по версионируемым правилам; неоднозначные и неизвестные форматы отклоняются.
- Криптографический слой (`jca_selftest`) использует Java Cryptography Architecture, проверяет обязательные алгоритмы и self-test при запуске; ошибка проверки блокирует защищённые операции.

### A-43. Старт реализации и инженерный процесс
- Сборка: Maven, Java 25, Paper 26.2.
- Первый этап: foundation — bootstrap, конфигурация, логирование, lifecycle и health.
- Архитектура: модульный монолит с чёткими пакетными границами и контрактами; первоначально один Maven-модуль.
- Тестирование: unit, integration и Paper runtime/smoke tests. Целевая Paper-проверка обязательна до объявления runtime-готовности.
- Разработка ведётся инкрементально; каждый этап сохраняет собираемость и сопровождается проверками.
- Разрешены изменения исходников, сборки, тестов, документации и CI непосредственно в репозитории RaskolZones.
